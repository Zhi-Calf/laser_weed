# 交给整车团队的稻行观测接口

## 分工与边界

我们负责图像采集接入、相机标定、分割/BEV/中心线算法、SDK、ROS 观测模块和联调记录。
整车侧负责全局作业行选择、作业/掉头切换、观测使用策略、转向、速度、故障停车及底盘通信。
`path_tracker` 已提供默认关闭的可选稻行 PID 消费模式，控制失败时降级到全局路径 LQR。
本模块不发布 `/chassis/cmd`，不改变 GNSS、全局路径或工作模式。
下文的有效性检查仅描述观测数据条件，不构成自动驾驶使能或控制策略。

## 输入输出

| 方向 | 默认话题与类型 | 约定 |
|---|---|---|
| 输入 | `/camera/image_raw` · `sensor_msgs/Image` | 原始畸变 BGR/RGB8，原分辨率、原采集时间；相机帧名必须匹配配置 |
| 可选输入 | `/gnss_driver/pose` · `weeder_msgs/Pose` | 只读复用组合导航姿态，启用 `attitude_gate` 后作为静态 BEV 的有效性检查 |
| 输出 | `/crop_row/observation` · `weeder_msgs/CropRowObservation` | 标定车体参考系下的一条选中导航中心线观测；不代表全部稻行 |
| 诊断记录 | 本地 JSONL 文件 | 只读记录工具生成，非机器人控制话题 |

图像订阅 best effort / volatile / KeepLast(1)；观测发布 reliable / volatile / KeepLast(1)。
消费方可用 reliable / volatile / KeepLast(1)，不应使用持久缓存来恢复历史有效状态。
同一观测话题只允许一个预期发布者；多相机/多算法时需使用独立话题并由整车侧明确选择。

## 坐标、单位与时间

车体参考系采用 x 向前、y 向左，单位 m、rad。SDK 中的直线为
`y = tan(heading_error_rad) * x + lateral_error_m`。

| 字段 | 含义 |
|---|---|
| `lateral_error_m` | x=0 处的截距，正值表示路径在车辆左侧 |
| `heading_error_rad` | 路径相对车体前向的方向，正值表示路径向左偏转 |
| `lookahead_m` | 拟合器前视范围参数，不表示横向误差在该距离处计算 |
| `confidence` | 算法组合评分，不是正确概率 |
| `processing_ms` | SDK 单次调用耗时 |
| `frame_age_ms` | 发布观测时距原始采集的总帧龄，包含排队和处理 |
| `header.stamp` | 原始图像的 ROS 采集时间，非发布/接收时间 |
| `header.frame_id` | BEV 实测对应的车体参考点，默认 `base_link` |

现有 LQR 使用“车辆相对路径”的误差，符号定义与 SDK 不同。
整车侧必须按其控制参考点和几何定义转换，不应直接复制字段进入 LQR。
相机内参、BEV、GNSS 杆臂与控制参考点需共同对齐；单独改 `frame_id` 不能替代标定。

SDK 内部用同机单调时钟，ROS 适配器负责从采集 ROS 时间映射。
接收方还需用自己的同源 ROS 时间检查 `now - header.stamp`，因为 `frame_age_ms`
不包含发布后的传输和接收排队。跨机器前应先验证时钟同步误差预算。
当前观察模块不支持仿真时间跳跃，回放使用当前播放时间并标记 `replay=true`。

## 已有 GNSS 姿态接入（静态门控 / 动态补偿）

本版可订阅现有 `gnss_localization` 的 `/gnss_driver/pose`，不新增组合导航解算，
不修改定位驱动，不发布 TF 或控制指令。使用 Pose 而非只读 `odom→base_link` TF：
该 TF 目前把 roll/pitch 设为 0；Pose 包含完整 roll/pitch/yaw 和 `valid`。

启用前，必须在**测量 BEV 的同一安装状态**记录参考 roll/pitch（rad），并核实
GNSS 姿态轴确实与 `vehicle_frame` 对齐。`pose_frame=odom` 只检查消息参考系名，
不进行传感器安装旋转变换。不能仅改帧名就将传感器坐标当成车体坐标。
确认后在配置中设 `reference_measured=true`、`vehicle_axes_confirmed=true` 和
`enabled=true`；参数均启动时生效，变更后重启。

规则：

- 姿态订阅采用 SensorDataQoS，最多保留 128 个样本，只使用采集时间不晚于图像的最新样本；
  不用未来姿态，不越过无效样本回退到旧的有效姿态，不等待补齐消息或做插值。
- 图像与定位必须使用同源 ROS 时钟，示例允许姿态比图像早最多 50 ms；
  不同话题乱序到达导致无可用样本时，该图像拒绝，后续帧可恢复。
- 要求恰好一个姿态发布者、帧名匹配、姿态有限、`Pose.valid=true`。
  当前驱动 `valid` 绑定 RTK 固定解，因此低解状态也会保守拒绝视觉观测。
- roll/pitch 相对 BEV 标定姿态超限时拒绝；示例阈值 0.035 rad（约 2°），
  只是待现场评估的参数，并不保证阈值内米制误差已达标。
- 姿态源时间倒退、重复或未来时间会锁定故障，需检查时钟后重启节点。
- 不符合条件时输出 `INVALID_INPUT`、NaN 导航量和置信度 0；原因写入 `detail`。
  检查通过时 `detail` 记录匹配龄期、roll/pitch 差值及静态 BEV 提示。

仅开启 `attitude_gate.enabled` 时，上述逻辑是静态 BEV 门控，不修正投影。
再开启 ROS 配置 `dynamic_bev.enabled`，并在 SDK BEV 文件启用及验收动态标定块，
则每帧把已匹配的绝对 roll/pitch 与单调时间戳传入 SDK 0.2 的
`rk_row_nav_process_with_attitude`，重算地面投影后执行原来的行提取/拟合/跟踪。
两处动态开关必须一致，否则节点拒绝启动；动态模式也必须启用姿态门控。
图像队列保存该帧匹配的姿态快照，不在工作线程中改用较新的姿态。

动态 SDK 配置需要明确的光学相机到车辆旋转、相机光心在车体中的位置、
车体参考点离地高度及 BEV 测量时的参考姿态。SDK 启动时检查物理模型与原实测
单应矩阵在参考姿态的一致性，不接受仅填写标记而几何不匹配的配置。
ROS 的参考姿态应与该 SDK 标定文件一致，相对变化阈值应覆盖已验证的补偿范围；
仍保留原静态 0.035 rad 示例阈值时，超过该值仍会拒绝，不能误以为补偿代码未调用。

该模型假定局部水平地面、车体参考点垂向高度恒定；不估计坡度、升沉、支架形变，
也不是视觉/GNSS 位置滤波。输出仍为车体 x/y 分量而非世界坐标。
没有有效姿态、时效不满足或投影退化时，拒绝输出有效导航量，不退回旧矩阵或静态模式。
默认全部关闭以保持旧配置兼容；关闭姿态门控时无姿态保护，节点会打印警告。
回放要验证此功能，必须同步回放原配套定位数据并映射到相同播放时钟；
不得将现场实时姿态与公开数据集/历史图片混配来证明几何正确。

迁入后已在 MyUbuntu 重跑动态 SDK 契约，以及真实 SDK 0.2 的 ROS 编译/链接测试。
节点 GTest 的姿态转发测试使用 fake SDK；SDK 动态几何测试只替换网络后端，
执行真实投影、提取和拟合。不能将两类测试合称为真实相机与模型的端到端导航验收。
现场参数、真实 GNSS/相机时间对齐及田间精度均未验收。
详见 `../row_nav_sdk/docs/migration-20261026.md`。

## 状态与生命周期

| 状态 | 消费约定 |
|---|---|
| `VALID` | 导航量有限；还需检查采集时间、会话、帧序号、坐标和 replay 标记 |
| `LOW_CONFIDENCE` / `NO_ROW` / `INVALID` | 无有效导航量 |
| `STALE` | 处理过程中或发布后监测到过期 |
| `NO_INPUT` | 尚无已处理图像，通常 `sequence=0`、`has_capture_time=false` |
| `INVALID_INPUT` | 图像、帧名、时间、缓冲区或启用的姿态检查不符合约定 |
| `SDK_ERROR` | SDK 调用失败或输出违反约定；同时检查返回码和 detail |

非 VALID 的导航量均为 NaN、置信度为 0，不能保留上一条数值代替。
启动失败会以非零码退出；节点直接退出/网络中断时可能没有最后一条失效消息，
整车侧必须有独立接收超时，不依赖状态心跳作为唯一故障检测。

`session_id` 每次节点重启改变；新会话重新建立帧序号与采集时间基线。
同一会话新帧序号递增，但允许丢帧/跳号；状态心跳可能沿用同一序号。
重复消息不能作为新采集数据刷新有效期。同一序号从 VALID 变 STALE 时应立即视为失效，
不能因为序号重复而忽略状态变化。标定或模型变更需重启并更换可追溯配置。
`replay=true` 的记录仅用于离线/台架核对，不能当作实车实时观测。

## 同事联调步骤

1. 按 README 构建，配置模型、同分辨率内参、车辆安装后的 BEV 和标定 ID。
2. 独立启动观察模块与相机；先不接控制，确认图像帧名、方向和参考点。
3. 启动下列只读记录工具，核对时间、符号、会话、状态和日志。
4. 分别测试遮挡/无行、断开相机、停止观察节点、重启节点、回放模式；
   由整车团队验证其消费方不会把旧观测或回放当作实时输入。
5. 整车团队确认接口后再安排控制联调；我们提供观测日志与算法问题定位支持。

```bash
ros2 run crop_row_perception record_observations.py --ros-args \
  -p output_path:=/absolute/new-test/observations.jsonl \
  -p max_frame_age_ms:=250.0
```

输出文件必须是新文件，已有文件会拒绝覆盖。Ctrl+C 后追加汇总记录。
JSONL 将 NaN/Inf 记录为 null，保留原始状态和契约错误。
`new_live_valid_observation` 只标识新的、及时的、非回放且数据检查通过的观测，
不代表允许行驶。汇总的 valid_frames 是模型发出 VALID 的帧数，不是精度或控制成功率。

## 验收还需要的现场输入

真实安装高度/俯角/参考点、同视角内参和 BEV、实际行距、现场图像/视频及人工核对。
公开数据集可以验证模型推理，但其图像不能套用现场相机的标定来声称米制导航正确。
本版也不提供全局作业行 ID，不能保证最近的视觉行就是规划要求的目标行；
行关联与控制使用条件由整车侧结合全局计划确认。
